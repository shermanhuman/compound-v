Compound V is installed. In every session:

- **Plans.** Write implementation plans in the `compound-v:plan` format, including in plan mode. Deliver the goal whole: one plan built to done, one PR per repository; split into stages only when the user asks or something forces it. Beyond a patch, before asking for approval, have a fresh reviewer run `compound-v:plan-review` and fold its findings in. Every plan beyond a patch has a home: the plan store the user's rules name (plan, revisions, decisions, reviews), otherwise an issue when the project uses a tracker (the plan in the body, reviews as comments). Search past plans and decisions before asking anything.
- **Reviews.** Changes headed for a pull request go through `compound-v:review-loop`, at the tier it picks, on a draft PR opened before the first round, and after every later push. Reviews and fix notes are posted on the PR or the plan's home, not kept in local files. Check your own work before each round, keep working while reviews run, and only must-fix findings earn another round.
- **Pull requests** follow `compound-v:pull-requests`. A PR targets the base branch the user's rules name (else the default); where they let you merge your own PR into that non-default base, do so when ready; otherwise the user merges. Never push to the default branch, force-push or rebase a PR branch (posted SHAs must stay valid), or route around a refusal.
- **Keep going.** While building an approved plan, don't end a turn announcing a next step you could take now: take it.
- **Deferred work** goes to the issue tracker: its own issue for a real piece of work, one "Follow-ups from #N" checklist issue for small leftovers. Never a local list.
- **Questions to the user.** A new goal starts with a restatement of its intent (`compound-v:plan`), after a conversation, one question at a time with your guess, where the request leaves it unclear. After that, one packet, not a drip in the chat: research first, then every open decision at once, each with its context, the options shown rather than described, and a recommendation `ok` accepts. Where the packet goes (a board the user's rules name first) is `compound-v:interrogate`'s *Present it once*. A step only the user can do is a task, after pushing back on yourself (`compound-v:interrogate`'s *Tasks for the human*). Where the user's rules name a board, a question that comes up mid-work goes there, a quick one too: with your default when its answer is cheap to undo, and you keep going on it (where the rules hold such answers for review, add how to undo it and get a second opinion); any other question (one whose answer can't be undone or is costly to undo, or one the plan can't be right without) waits there for the answer, and you carry on with the work it doesn't touch. Where the rules batch work (a start packet, a review at the end), foreseeable questions go in the start packet. Don't end a turn on such a question in the chat or the question tool. **Answer where the user engages:** the user is in the session when the turn you're in began with a message they typed there; a board answer, a hook's message or a notification relayed into the session isn't them. Where a board is named, even in a session the user started, only two kinds stay in the session: intent questions before the restatement, and a direct reply to what the user just typed (a question back about it included). A goal started from the board has its intent questions on the board as one ask, each with your guess; the user can answer some, skip any and submit at once, so mark a question an earlier answer would make moot ("skip if 1 is team"). Where no board is named, a single quick question with nothing to show can stay in the chat or the question tool, with nothing the user needs sitting only in text before the widget.
- **Link issues and PRs.** Every time you mention one to the user, numbered or not, link the URL the tracker reports: `[#123](<URL>)`, or `[repo#45](<URL>)` across repositories.
